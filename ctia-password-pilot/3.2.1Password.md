# CTIA 3.2.1 Password Test Guide

## 1. Purpose

This guide explains how to exercise CTIA Cybersecurity Certification Test Plan Version 2.2, Section 3.2.1, against the CTIA Password Pilot.

It paraphrases the intent of each CTIA test case and provides pilot-specific preparation, test actions, expected behavior, pass/fail criteria, cleanup, and suggested evidence. The CTIA test plan remains the controlling source. An Authorized Test Lab (ATL) must use its authorized procedures and resolve any difference between this guide and the official test plan.

## 2. Pilot credential model

The pilot deliberately uses a shared default credential:

- Username: `admin`
- Password: `admin`

This is a **default password**, not a unique factory-set password. The default permits entry only into mandatory password enrollment. The pilot blocks normal operation until the password is replaced.

The distinction matters for applicability:

- Test case 3.2.1.1 evaluates a unique factory-set-password design. The pilot does not implement that design. Record this case as not applicable to the selected pilot credential model, with the rationale that the shared-default path is evaluated under 3.2.1.2. If an ATL applies 3.2.1.1 literally to every preconfigured credential, `admin` is generic and the result would be a failure. Confirm the expected treatment with the ATL.
- Test cases 3.2.1.2, 3.2.1.4, 3.2.1.6, and 3.2.1.10 apply to the pilot's shared-default design.

## 3. Test environment

### 3.1 Required components

- Kali Linux host with Docker and Docker Compose.
- CTIA Password Pilot source and built container image.
- A browser on the Kali host.
- Access to <http://127.0.0.1:8080> or <http://localhost:8080>.
- Permission to run Docker commands for setup and factory reset.
- A location outside the container for screenshots, notes, and exported logs.

### 3.2 Start and verify the DUT

From the `ctia-password-pilot` directory:

```bash
docker compose up --build --detach
docker compose ps
curl --fail http://127.0.0.1:8080/healthz
```

Expected health response:

```json
{"profile":"CTIA 3.2.1","status":"ok"}
```

Open <http://127.0.0.1:8080> in the Kali browser.

### 3.3 Restore a known initial state

Run the host-side reset before any test that requires a fresh device:

```bash
./reset-to-default.sh
```

The reset:

- Invalidates all sessions.
- Removes added users.
- Restores the default device configuration.
- Restores `admin/admin`.
- Requires password enrollment before normal operation.

This is destructive and should be treated as the pilot equivalent of pressing a physical router or CPE reset button.

### 3.4 Suggested test data

| Purpose | Value | Expected behavior |
|---|---|---|
| Shared default password | `admin` | Accepted only for initial enrollment; rejected as a replacement and during normal operation |
| Valid fresh admin password | `Pilot9!safe` | Accepted |
| Valid operator password | `Role9!safe` | Accepted |
| Less than 8 characters | `Ab7!xy` | Rejected |
| More than 2 repetitive characters | `aaabbccd` | Rejected |
| More than 2 sequential characters | `123ab457` | Rejected |
| Incorrect login password | `Wrong9!pass` | Rejected |

The pilot interprets "repetitive" as three identical contiguous characters. It interprets "sequential" as three contiguous ascending or descending ASCII letters or digits.

## 4. Evidence and result recording

For each test case, record:

- Test case ID.
- Date and tester.
- Container image ID.
- Browser and version.
- Initial state and user role.
- Exact test input, except do not place a production secret in evidence.
- Observed result.
- Pass, fail, or not applicable disposition.
- Screenshot, HTTP response, or relevant log reference.
- Cleanup performed.

Capture the image ID before testing:

```bash
docker image inspect ctia-password-pilot-password-pilot \
  --format '{{.Id}}'
```

Capture application logs when needed:

```bash
docker compose logs --no-color password-pilot
```

Do not treat the automated unit-test output as a substitute for ATL observations. It is supporting regression evidence only.

## 5. Recommended execution order

To minimize resets and rate-limit interference:

1. Reset the pilot.
2. Evaluate 3.2.1.1 applicability and execute 3.2.1.2.
3. Enroll `Pilot9!safe` as the new administrator password.
4. Execute 3.2.1.3, 3.2.1.5 through 3.2.1.7, 3.2.1.9 through 3.2.1.11, and 3.2.1.16.
5. Create an operator and execute 3.2.1.8, 3.2.1.14, and 3.2.1.15.
6. Execute rate limiting in 3.2.1.12. Wait at least 60 seconds or reset afterward.
7. Execute successful authentication in 3.2.1.13.
8. Execute factory-reset behavior in 3.2.1.4 last because it removes users and sessions.

## 6. Test procedures

### 3.2.1.1 - Factory-set password uniqueness

**CTIA requirement, paraphrased:** A manufacturer-set password must be unique per device and must not be a generic or obviously derived value.

**Applicability to the pilot:** The pilot intentionally implements the shared-default alternative, not a unique factory-set credential. The applicable behavioral path is 3.2.1.2.

**Procedure:**

1. Reset the pilot with `./reset-to-default.sh`.
2. Review the documented initial credential in `README.md` and on the login page.
3. Confirm that the documented credential is `admin/admin` for every fresh pilot instance.
4. Record that this is a generic shared default and that the device requires its replacement under 3.2.1.2.

**Expected observation:** The pilot does not claim or demonstrate a unique per-device factory-set password.

**Disposition:** Record **N/A for the unique factory-set-password path**, with the shared-default rationale. If the case is applied literally to the pilot's preconfigured `admin` value, record **Fail** because it is generic. Obtain ATL agreement on the chosen disposition.

**Evidence:** Login-page screenshot, README reference, and applicability rationale.

### 3.2.1.2 - Shared default changed before normal operation

**CTIA requirement, paraphrased:** When multiple devices share a default password, the device must block normal operation or force the user to replace it during initial setup.

**Precondition:** Fresh-device state.

**Procedure:**

1. Browse to <http://127.0.0.1:8080>.
2. Sign in with username `admin` and password `admin`.
3. Observe the destination page.
4. Without changing the password, try to browse directly to <http://127.0.0.1:8080/>.

**Expected observation:** The browser is redirected to **Replace the shared default**. Direct access to the overview or other normal-operation pages is also redirected to password enrollment. Only password change and sign-out are available.

**Pass:** Normal operation cannot begin before the shared default is replaced.

**Fail:** The overview, device configuration, user management, or another normal-operation function is available while `admin` remains the password.

**Evidence:** Screenshot of the mandatory replacement page and the redirected URL.

### 3.2.1.3 - Accessible password management

**CTIA requirement, paraphrased:** The password-change mechanism must be readily accessible.

**Precondition:** Complete initial enrollment with `Pilot9!safe` and remain signed in.

**Procedure:**

1. Inspect the primary navigation.
2. Select **Password**.
3. Confirm that the page contains current password, new password, and confirmation fields.

**Expected observation:** The password mechanism is directly available from the main navigation without hidden menus or undocumented URLs.

**Pass:** An authenticated user can readily locate and open the password-change page.

**Fail:** The mechanism is absent, inaccessible, or requires an undocumented path.

**Evidence:** Screenshot showing the navigation and password page.

### 3.2.1.4 - Password behavior after factory reset

**CTIA requirement, paraphrased:** After setting a fresh password and restoring factory settings, a shared default must not allow normal operation without another mandatory change.

**Precondition:** Administrator password is `Pilot9!safe` and the pilot is in normal operation.

**Procedure:**

1. Select **Device**.
2. Select **Reset pilot device** under **Factory reset**.
3. Confirm that the session is invalidated and the login page appears.
4. Sign in with `admin/admin`.
5. Attempt to open the overview without setting a new password.

The physical-reset equivalent may also be exercised without login:

```bash
./reset-to-default.sh
```

**Expected observation:** The previous password no longer authenticates, `admin/admin` enters only mandatory enrollment, and normal operation remains blocked.

**Pass:** Factory reset restores the provisioning state and forces replacement of the shared default.

**Fail:** The device enters normal operation with `admin`, retains the previous normal-operation session, or does not restore the documented factory behavior.

**Evidence:** Before-reset normal-operation screenshot, reset action, post-reset login, and mandatory replacement page.

### 3.2.1.5 - Minimum password length

**CTIA requirement, paraphrased:** A fresh password shorter than eight characters must be refused or produce a notification requiring at least eight characters.

**Precondition:** Authenticated as a user whose current password is known.

**Procedure:**

1. Open **Password**.
2. Enter the current password.
3. Enter `Ab7!xy` in both new-password fields.
4. Attempt to save.

**Expected observation:** The browser or server refuses the value and indicates that at least eight characters are required. The existing password remains valid.

**Pass:** The shorter value is not stored.

**Fail:** The shorter value becomes the user's password.

**Evidence:** Validation message and a subsequent successful login using the unchanged password.

### 3.2.1.6 - Reuse of the shared default

**CTIA requirement, paraphrased:** A user must not be able to change the password back to the shared default.

**Precondition:** Normal operation after replacing `admin` with `Pilot9!safe`.

**Procedure:**

1. Open **Password**.
2. Enter `Pilot9!safe` as the current password.
3. Enter `admin` as the new password and confirmation.
4. Attempt to save.

**Expected observation:** The value is rejected. The browser can reject it for being too short; the server independently rejects it because it equals the shared default.

**Pass:** `admin` is not stored as the new password and `Pilot9!safe` remains valid.

**Fail:** A normal-operation account can be changed back to `admin`.

**Evidence:** Rejection message and subsequent authentication with the unchanged password.

### 3.2.1.7 - Repetitive-character restriction

**CTIA requirement, paraphrased:** A proposed password containing more than two repetitive characters must be refused.

**Precondition:** Authenticated user with a known current password.

**Procedure:**

1. Open **Password**.
2. Enter the current password.
3. Enter `aaabbccd` as the new password and confirmation.
4. Attempt to save.

**Expected observation:** The pilot reports that the password cannot contain more than two repetitive characters.

**Pass:** `aaabbccd` is rejected and the current password remains valid.

**Fail:** `aaabbccd` becomes the user's password.

**Evidence:** Rejection message and unchanged-password login.

### 3.2.1.8 - Password confidentiality between users

**CTIA requirement, paraphrased:** The most privileged user must not be able to obtain another user's current password. Resetting another user's password does not justify disclosure of its current value.

**Precondition:** Authenticated as `admin` with `Pilot9!safe`.

**Procedure:**

1. Open **Users**.
2. Create an operator with username `operator` and password `Role9!safe` if one does not already exist.
3. Inspect the user list and all available administrator controls.
4. Attempt to locate or display the operator's password.
5. Sign out, authenticate as `operator`, and confirm that the operator does not have access to **Users**.
6. While authenticated as `operator`, browse directly to <http://127.0.0.1:8080/users>.

**Expected observation:** The administrator sees username, role, and enabled status only. Neither password values nor hashes are displayed. The operator receives HTTP 403 when requesting the administrator-only users page.

**Pass:** No user can obtain another user's current password through the DUT interface.

**Fail:** A password value or reusable equivalent is disclosed.

**Scope note:** Docker-host access represents physical or platform-administrative access and is outside this Web UI account test. Database contents are password hashes, not plaintext passwords.

**Evidence:** Administrator user-list screenshot and operator HTTP 403 observation.

### 3.2.1.9 - Concealed password entry

**CTIA requirement, paraphrased:** Password characters must be concealed when entered on a device display.

**Precondition:** Login or password-change page is open.

**Procedure:**

1. Type a test password in the login password field.
2. Inspect the displayed characters.
3. Repeat for the current, new, and confirmation fields on the password-change page.

**Expected observation:** Each field displays masking symbols rather than the entered password characters. The fields are HTML `type="password"` controls.

**Pass:** Passwords are concealed in every password-entry field.

**Fail:** Any password field displays the entered value in clear text by default.

**Evidence:** Screenshot showing masked input. Do not include an actual sensitive password in test evidence.

### 3.2.1.10 - Default password rejected during normal operation

**CTIA requirement, paraphrased:** After provisioning, authentication using the shared default password must fail.

**Precondition:** Initial enrollment is complete and the current administrator password is `Pilot9!safe`.

**Procedure:**

1. Sign out.
2. Attempt to sign in as `admin` using password `admin`.

**Expected observation:** Authentication fails with the generic message **Invalid username or password**. No authenticated session is created.

**Pass:** Login with `admin/admin` is unsuccessful.

**Fail:** The default credential authenticates during normal operation.

**Evidence:** Rejection screenshot and absence of access to the overview page.

### 3.2.1.11 - Incorrect password rejection

**CTIA requirement, paraphrased:** Authentication with an incorrect password must fail.

**Precondition:** Administrator is enrolled with `Pilot9!safe`.

**Procedure:**

1. At the login page, enter username `admin`.
2. Enter `Wrong9!pass` as the password.
3. Submit the form.

**Expected observation:** Authentication fails with a generic error and the login page remains displayed.

**Pass:** The incorrect password does not create a session.

**Fail:** The incorrect password authenticates or exposes protected content.

**Evidence:** Rejection screenshot. Application-level inspection should observe HTTP 401 for the failed form submission.

### 3.2.1.12 - Successive failed-attempt restriction

**CTIA requirement, paraphrased:** After the manufacturer-defined threshold, authentication attempts must be restricted to no more than five per minute.

**Pilot policy:** Five failed attempts are allowed per username and client address in a rolling 60-second window. Attempts after the fifth receive HTTP 429 until the rolling window advances. The restriction is checked before password validation, so a correct password is also blocked during the active limit.

**Precondition:** No recent failed attempts for username `admin` from the test client. Reset the pilot or wait at least 60 seconds if uncertain.

**Procedure:**

1. Record the start time.
2. Submit `admin/Wrong9!pass` five times from the same browser and host address.
3. Submit a sixth authentication attempt within the same 60-second window.
4. Optionally submit the correct password while the limit remains active.
5. Wait until more than 60 seconds have elapsed since the relevant failed attempts, then submit the correct password.

**Expected observation:** The first five attempts fail as invalid credentials. The sixth and any additional attempt in the active window are rejected with **Too many failed attempts** and HTTP 429. Authentication becomes available again after the rolling window expires.

**Pass:** The DUT permits no more than five attempts in the applicable one-minute window after the threshold is reached.

**Fail:** A sixth attempt is processed normally within the same active window, or the restriction can be bypassed using the same username and client address.

**Evidence:** Timestamped observations, rate-limit message, HTTP 429 response, `Retry-After: 60` header, and successful recovery after the window.

**Cleanup:** Wait at least 60 seconds or run `./reset-to-default.sh` and reenroll before continuing.

### 3.2.1.13 - Correct password accepted

**CTIA requirement, paraphrased:** Authentication using the correct password must succeed.

**Precondition:** Administrator is enrolled with `Pilot9!safe` and no rate limit is active.

**Procedure:**

1. Sign out.
2. Enter username `admin` and password `Pilot9!safe`.
3. Submit the form.

**Expected observation:** The overview page opens and identifies the authenticated role as `admin`.

**Pass:** The correct credential creates an authenticated session and permits access appropriate to the role.

**Fail:** The correct credential is rejected when the account is enabled and no rate limit is active.

**Evidence:** Overview screenshot showing the authenticated username and role.

### 3.2.1.14 - Incorrect password rejected for every role

**CTIA requirement, paraphrased:** When more than one authenticated role exists, an incorrect password must fail for each role.

**Precondition:** Create these enabled accounts:

- `admin` with password `Pilot9!safe`
- `operator` with password `Role9!safe`

**Procedure:**

1. Sign out and attempt `admin/Wrong9!pass`.
2. Confirm rejection.
3. Attempt `operator/Wrong9!pass`.
4. Confirm rejection.

**Expected observation:** Both attempts fail with the same generic authentication error. Neither account receives a session.

**Pass:** Incorrect passwords fail for both the administrator and operator roles.

**Fail:** An incorrect password succeeds for either role.

**Evidence:** Separate observations for each role. Do not repeat enough failures to unintentionally activate 3.2.1.12.

### 3.2.1.15 - Correct password accepted for every role

**CTIA requirement, paraphrased:** When more than one authenticated role exists, the correct password must authenticate each role.

**Precondition:** The `admin` and `operator` accounts from 3.2.1.14 exist and no rate limit is active.

**Procedure:**

1. Sign in as `admin` using `Pilot9!safe`.
2. Confirm the overview identifies role `admin` and that **Users** and **Device** are available.
3. Sign out.
4. Sign in as `operator` using `Role9!safe`.
5. Confirm the overview identifies role `operator` and that administrator-only navigation is absent.

**Expected observation:** Both correct credentials authenticate. Each account receives only the functions assigned to its role.

**Pass:** Correct credentials successfully authenticate both roles.

**Fail:** A correct credential is rejected for an enabled role, excluding an active rate limit.

**Evidence:** Separate overview screenshots for the administrator and operator sessions.

### 3.2.1.16 - Sequential-character restriction

**CTIA requirement, paraphrased:** A proposed password containing more than two sequential characters must be refused.

**Precondition:** Authenticated user with a known current password.

**Procedure:**

1. Open **Password**.
2. Enter the current password.
3. Enter `123ab457` as the new password and confirmation.
4. Attempt to save.

**Expected observation:** The pilot reports that the password cannot contain more than two sequential characters.

**Pass:** `123ab457` is rejected and the existing password remains valid.

**Fail:** `123ab457` becomes the user's password.

**Evidence:** Rejection message and a subsequent login using the unchanged password.

## 7. Automated regression checks

Run the supporting test suite from the project directory:

```bash
docker compose run --rm --no-deps \
  -e CTIA_DATA_DIR=/tmp/ctia-test-data \
  -v "$PWD/tests:/tests:ro" \
  password-pilot python -m unittest discover -s /tests -v
```

The automated suite checks mandatory first-use change, password rules, default rejection, failed-attempt restriction, correct login, role authorization, factory reset, the no-login reset command, and removal of the former `/test-plan` Web UI page.

```bash

```
